## 删除条入场动画对齐导航栏（360ms）+ 一次操作失误的复盘

**用户诉求**：「那个删除记录几个字弹出太快了，数值改成和导航栏一样的」。

**根因**：删除条搬成 Index 的覆盖层后**丢了入场动画** ——
它挂在详情页的 `barEntered` 状态上，而组件已搬到 Index，
**状态与组件不同属 → 动画彻底失效**，条件渲染导致出现即最终态（「啪一下蹦出来」）。

**修**：
- 动画状态迁到 Index 的 `@State slotDeleteIn`（与删除条同组件）；
- 时长/曲线对齐导航栏：`CAPSULE_ANIM_MS(360)` + `Curve.EaseOut`
  （胶囊返场同款，两者互为逆过程）；
- 动作：`translate(56) + scale(CAPSULE_EXIT_SCALE) + opacity 0` → 恢复全量，
  即「被 ＋ 钮吐出来」；
- `onAppear` 里 `setTimeout(16)` 再置 true（**同帧改变量不触发补间**，ArkUI 限制）；
- 复位放在 `animateCapsule` 的返场分支，**不放 build()**；
- 删除详情页残留的 `@State barEntered`（已失效的死状态）。

## ⚠️ 记录详情下半页消失 —— layoutWeight 抢占事故（我自己造的）

**用户反馈**：「我记得这个页面是很长的，很多数据，是不是被什么覆盖掉了」
（截图：HeroCard 之下整片空白，「行为快照」「记录来源」两个区块全不见）。

**代码其实完好**：`HeroCard/Snapshot/SourceCard/InfoRow` 的**定义与调用都在**，
不是被删、也不是被遮 —— 是**渲染不出来**。

**根因（上一轮我加的）**：把删除条移出本页时，我顺手加了一个「占位元素」：
```typescript
Column().layoutWeight(1)     // ← 罪魁祸首
```
它和上面的 `Scroll().layoutWeight(1)` **抢权重** → Scroll 只剩 HeroCard 那么高，
下面的内容全部被挤出可视区。用户的直觉「被覆盖掉了」完全正确。

**修**：删掉该占位元素（删除条是**覆盖层**、本就不占布局，页面无需任何占位），
并把 Scroll 的 bottom padding 从 `Space.XL` 提到 **96**
（= 56 删除条 + 24 呼吸 + 16 安全区），保证最后一行能滚到删除条上方。

**构建**：BUILD SUCCESSFUL（24s，0 error）。

### 沉淀（本轮最值得记的一条）

1. **`layoutWeight` 是「抢」不是「加」**：同一父容器下放两个
   `layoutWeight(1)`，它们会**均分**剩余空间 —— 加一个"占位"元素很可能
   把真正需要撑开的主体（Scroll）压扁。**不需要占位就不要加。**
2. **"内容消失"先分清是没渲染还是没画出来**：
   先 `grep` 定义与调用是否都存在（本例都在）→ 再查布局约束（本例是权重被抢），
   不要一上来就怀疑"被覆盖"或"被删代码"。
3. **上一轮改动引入的副作用，往往要在下一轮才暴露**（改了 A 结构，
   加了 B 占位，用户的截图要到装包后才看到）。
   凡是动了 `layoutWeight` / 条件渲染结构，装包前要自己先想一遍
   「同一父容器下还有谁在抢权重」。

## 胶囊退场动画流畅度 + 删除条玻璃质感重做

**用户诉求**：「优化一下这段动画，有点不流畅，可能是冲突，然后改一下那个删除键的液态玻璃状态，有点丑，你美化一下」。

### ① 动画不流畅的根因：位移量过大（不是属性冲突）

用户以为是"属性冲突"，实测是**物理量不匹配**：
- 原位移 `w/2 + 38` ≈ **300vp**，而胶囊只有 56vp 高；
- 时长 360ms → 平均速度 **>800vp/s**，肉眼是"被甩出去"而非"被吸进去"；
- 胶囊带 `backdropBlur`（每帧重建离屏渲染层），位移面积越大 → 重算越多 → 越卡。

**修**：
| 项 | 旧 | 新 |
|---|---|---|
| 位移 | `w/2 + 38`（≈300vp） | `w*0.5 + 30`（**减半**） |
| 缩放 | 0.12（压成一个点） | **0.34**（保留"小胶囊滑进加号"语义） |
| 曲线 | EaseInOut（双向） | 退场 **EaseIn** / 返场 **EaseOut**（互为逆过程） |

### ② 删除条玻璃"红塑料板"的三处病因

| 病因 | 旧值 | 新值 |
|---|---|---|
| 染色过厚 → 盖住 blur、液态感归零 | 0.22 / 0.26 | **0.10 / 0.13** |
| 纯红描边箍死胶囊，与冷白受光边一比显脏 | 0.46/0.52 纯红 | 上边冷白+暖红调 0.22、左边纯冷白 0.34、背光 0.14 |
| 图标与文字同色同权重 → 红色面积翻倍 | 都是 Accent.DANGER | 图标 17px 深红、文字 SMALL 降一档红（#C4554C/#F2A49D） |

**思路：玻璃先成立、danger 其次**。染色回到与导航胶囊同一量级，
danger 语义交给**文字与图标**而不是整块色 —— 这才像"玻璃上刻着红色的字"，
而不是"一块红色塑料"。

**构建**：BUILD SUCCESSFUL（19s，0 error）。

### 沉淀

1. **动画卡顿先量物理量**：位移量 ÷ 时长 = 平均速度，
   超过 ~500vp/s 肉眼就会觉得"被甩"而不是"被吸入"。
2. **带 `backdropBlur` 的组件做大位移必然掉帧** —— 离屏层每帧全量重算，
   位移面积与耗时成正比。缩放系数别调太小（0.12 → 缩成一个点也失去了叙事）。
3. **进出场用互为逆过程的曲线**（EaseIn / EaseOut）比双向 EaseInOut 更自然。
4. **半透明材质的 alpha 不能按"材质强度"直觉给**：染色 0.2+ 就等于不透明色块，
   `backdropBlur` 完全失效。玻璃染色应与同级玻璃面同量级（≤0.15）。

## 删除条宽度 = 胶囊实测宽（最终形态）

**用户诉求**：「让删除记录的宽度和底部导航胶囊宽度一样，长度也一样」。

**做法**：删除条是底栏 `Row` 的**兄弟覆盖层**（不能放进 Row，否则打乱权重），
所以**不能用百分比占满**，只能取具体宽度。直接复用胶囊的实测值：

```typescript
// Index.ets

...
if (this.capsuleGone && this.barSlotDelete) {
  Row() { this.DeleteBarInSlot() }
    .position({ left: Space.PAGE, bottom: Space.XS })
    .width(this.capsuleW > 0 ? this.capsuleW : 300)   // ← 与胶囊等宽，且自动同步

}
```
胶囊多宽删除条就多宽、左缘同样锚在 `Space.PAGE` 上，**换机型/字体缩放自动跟随**，
无需改任何常量（此前写死 `right: PAGE+66` 只能近似，换机型就会错）。

```typescript
const w = this.capsuleW > 0 ? this.capsuleW : this.barW   // 未就绪时兜底

### 方法论沉淀（本轮最重要的一条）

**「元素在动画中漂移」要查位移基准量是否稳定，而不是先调动画参数。**
- 现象：＋ 钮进二级页「往左一点」
- 我第一反应是布局/权重问题（甚至改坏了胶囊宽度，见上轮教训）
- 真因：位移公式的输入 `barW` 挂错了对象（内容宽度而非容器宽度），
  内容宽度在 visibility 切换时会变 → **用会变的量算位移，终点必然漂移**

推论：**凡是 `x = f(测量值)` 形式的动画位移，测量值必须挂在「不随状态变化的元素」上**。
本项目已有两处同类测量，语义必须区分清楚：
- `barW` = 内层 4 格文字 Row 宽 → **仅用于药丸分格**（`pillX = 选中序号 × cellW`）
- `capsuleW` = 外层胶囊宽 → **仅用于退场位移**
- `contentW` = Tab 内容区宽 → 用于整页滑动

.margin({ right: Space.SM, ... })     ↑ ② 又给每个 chip 无条件加右间距
```
实际占位 = `cellW + 间距` > 可用宽的一半 → Flex 每行只塞得下 1 个 →
4 个 chip 竖排 4 行，且每行右侧空掉一格。
**两个 bug 叠加**：① 间距扣两次；② **每行末列也挂了 margin**，
右边凭空多出一个空档，即使能放下第二个也会被顶走。

**修复（间距口径配套）**：
- `chipCellW()` 保持扣 `(PER_ROW-1) × 间隔`（这是正确的整行口径）；
- margin 改为**按列位判断**：`right: chipCol(key) < PER_ROW-1 ? Space.SM : 0`；
- 新增 `chipCol(key)`：`i % CHIP_PER_ROW` 求列位。

**构建**：BUILD SUCCESSFUL（46s，0 error）。

**方法论沉淀**：
1. **均分格宽 + margin 必须配套**：格宽里扣了列间距，就只能给**非末列**加
   margin；两处同时无条件加 = 间距翻倍 → 每行放不下预期数量。
   这与「`layoutWeight` 由包裹层承担、组件自身只声明 width」是同一类错误：
   **同一个量只能在一个地方表达**。
2. 「N 个元素排 M 列」的排版 bug，先查两件事：
   ① 格宽公式是否已扣间距 ② margin 是否给到了末列。本例两者都错。
3. Flex 折行的表现异常（预期 2 列却成 1 列）几乎都是**实际占位宽度超标**，
   而不是 Flex 本身有问题。

## 记录详情底部删除条：改成从「＋」圆钮弹出的液态玻璃胶囊

**用户诉求**（两张截图对照）：

2. **动效要有"来由"**：凭空淡入的控件没有叙事感。

3. **状态语义靠颜色元素而非色块承载**：危险操作若用整块粉底会毁掉玻璃材质，

## 科普页选中 chip：深色下改为白色（并修掉一个模块级 const 陷阱）

**用户诉求**：「把这个在深色模式下换成白色」（截图红圈圈住「全部」选中 chip，
深色下几乎看不出选中态）。

**根因**：深色下 `activeBg` 写的是 `rgba(255,255,255,0.14)` ——
**只叠 14% 白**，在深底上等于没画。既看不出「选中」，
近白字压上去也发飘（用户此前反馈过「被选中后字体看不清」的同源问题）。

**顺带发现并修掉的隐患（更重要）**：
`CHIP_ACTIVE_FG` 原声明为**模块级 const**：
```typescript
const CHIP_ACTIVE_FG = ThemePalette.dark ? '#F2F5F3' : '#1A1F1C'
```
模块级 const 在**模块加载时求值一次**就固定。若深色模式是页面建好之后
才由 `ThemeMode.init()` 换血的，这个常量**永远停在浅色值** ——
深色下就是「深底 + 近黑字」，完全看不见。
改为 `function chipActiveFg(): string`，每次 build 现取。
这与 GlassPill 注释里写的「成员字段初值只在构造时求值一次，
static 换血不会回灌」是**同一个坑的模块级版本**。

**修复**：
- `activeBg`：深浅**统一** `'rgba(255,255,255,0.92)'`（不再分叉）——
  深色下就是一块实白芯片；
- `chipActiveFg()` 统一返回近黑 `'#1A1F1C'`，
  近白底 vs 近黑字 ≈ **17:1，全应用对比度最高处**；
- GlassPill 对 active 态会自动把 gloss 降到 0.5（实底上高光克制），
  实白底上不会出现塑料感过曝，无需额外处理。

**构建**：BUILD SUCCESSFUL（21s，0 error）。

**方法论沉淀**：
1. **模块级 `const` + static 色值 = 最隐蔽的换血失效**。
   `const X = ThemePalette.dark ? A : B` 与组件成员字段
   `x: string = ThemePalette.dark ? A : B` 是**同一个坑**，
   都在首次求值后冻结。凡是依赖 `ThemePalette.dark` 的值，
   一律写成**函数**或**私有方法**（每次 build 现取）。
2. 半透明色值在深色下要**重新评估 alpha**：`0.14` 白在浅色底上
   是"轻透"，在深色底上就是"什么都没有"。同一组 alpha 不能跨明暗复用。
3. 「选中态」这类**状态指示**必须做到「一眼可辨」优先于「材质统一」——
   深色下强行把白底压暗去融入深色底，牺牲的是可辨识度，得不偿失。

## 分段控件「双层玻璃」修复（筛选栏套娃）

**用户诉求**：「这里的液态玻璃为什么是双层，修一下」（记录页截图，红圈圈住
「全部/出行/节能/回收/饮食」筛选栏）。

**根因：外层 Stack 与内层轨道各画了一套玻璃，套成"壳中壳"**：
```
Stack(padding 3) {
  ├ 轨道 Row  → linearGradient(surface(SEGMENT_TRACK_BG)) + borderColors()   ← 内层玻璃
  ├ 选中药丸 → 135° 品牌渐变实底（不透明，本不算玻璃）
  └ 文字层
}
  ← 外层自身还挂了 linearGradient(surface(CARD_BG)) + borderColors() + shadow()  ← 又一层玻璃
```
外层 padding(3) 让内层轨道缩进一圈，于是**两道 1px 描边叠在 3vp 缝隙里互相加亮**，
视觉上就是「一个玻璃圆角框里又套一个玻璃圆角框」。

**这是历史遗留**：早年为修「筛选栏边缘生硬」给外层加了玻璃+四边异色描边，
内层轨道本来就是玻璃 —— 两者叠加成双层，却一直没人指出。

**修复：统一为「单层玻璃」范式**
- `RecordListPage.FilterBar` / `BehaviorAddSheet` 分类栏：
  外层 **删掉** `linearGradient(surface(CARD_BG))` + `borderColors()` + `shadow()`，
  改为 `.backgroundColor(Color.Transparent)`，
  外层只保留三件事：`.clip(true)`（裁药丸溢出）、`.borderRadius(PILL)`、
  `.onAreaChange`（测宽供药丸平移）。
- 玻璃职责**全部交给内层轨道**（唯一一套渐变 + 四边异色描边）。
- 与 Index 底部导航胶囊、全库 CfCard 统一为同一范式。

**全库审计**：`grep "Stack({ alignContent: Alignment.Start })"` + `shadow(Shadow.card())`
共 28 处，逐个确认**都是单层 CfCard**（卡片自带阴影），无其他"玻璃套玻璃"。
本类双层仅此两处分段控件。

**踩坑**：顺手把 `onAreaChange` 的 `area.width as number | string` 收窄成 `as number`，
编译报 `Argument of type 'Length' is not assignable to parameter of type 'string | number'`
—— `Area.width` 是 `Length`（含 Resource 类型），**必须保留 `as number | string` 联合入参**，
由接收方再自行判类型（现有 `onFilterTrackArea` 已是这个写法，别改）。

**构建**：BUILD SUCCESSFUL（21s，0 error）。

**方法论沉淀**：
1. **玻璃材质不可嵌套**：玻璃本身是半透明 + backdropBlur，套两层会
   ① 两道描边在缝隙互亮 ② 两层模糊各建离屏层（性能白费）③ 观感变成"壳中壳"。
   一个视觉区域**有且只有一层** `linearGradient(surface(...))` + `border(...)`。
2. 「边缘生硬 / 想加玻璃感」的正确做法是**加厚那一层**（调 surface 参数），
   而不是**再包一层玻璃**。
3. 分段控件的职责分层：外层容器只做 clip + 尺寸测量，**不画任何材质**。
4. ArkUI `Area.width` 类型是 `Length`，跨函数传递时联合入参不能收窄。

## 三个问题：深色副标题看不见 / 科普页没情绪可视化 / 深色文字该多亮

**用户诉求**（三张截图）：
① 「这个字体看不清」（"我的"页列表副标题）
② 「这里的 UI 没有做碳情绪可视化」（科普页 ALERT 档）
③ 「深色模式这里字体要不要变成白色」

### ① 副标题对比度 1.00:1 —— 根因是令牌假定「背景恒为中性」

**取证**（截图逐像素，分位取文字笔画 / 中位取卡片底）：
```
副标题 Neutral.TEXT_MUTED vs 卡片底 #3B2C29 = 1.00:1  ← 完全隐形
主标题 Neutral.TEXT(#E9F0ED) vs 同底         = 7.85:1  ← 清晰
```
同一行、同一底色，一个看得见一个看不见。

**根因（设计盲区，不是配错值）**：
`TEXT_SUB` / `TEXT_MUTED` 是按**冷灰绿底**（#182421，NONE_SOLID）调的，
而截图所在页面是 **ALERT 档**：`*_SOLID` 换成暖棕红 #2A1C1A、卡片再叠暖调
→ 底色整体偏暖偏红。**冷调灰字压在暖调底上，Rec.709 亮度几乎相等 → 对比度归零。**
即：次级文字色**假定了背景恒为中性色，没考虑碳情绪会把底色染成暖色**。

**修**：`TEXT_SUB #9DB1AC → #B4C4BF`、`TEXT_MUTED #74847E → #9AA8A3`
（整体提亮约 1.5 级并微加暖）。实测 ALERT 底上 **3.39 → 5.39:1**，
层级仍清晰：正文 11.50 > 副标题 7.34 > 弱文 5.39。

**回答用户的第③问**：**不该变成纯白**。三个理由——
① 白字会和主标题（11.50:1）拉不开层级，副标题就失去"次要"语义；
② 一屏里 5 行副标题全用纯白 = 满屏白字，视觉噪音比现在的看不清更糟；
③ 正确做法是**提亮到"能读"而非"最亮"** —— 5.39:1 已远超 WCAG 弱文 3.0。

### ② 科普页碳情绪可视化

**先澄清**：该页**本来就有**碳情绪（根底用 `EcoTheme.bgSolid(ecoLevel)`，
截图底部那道暖橙光晕就是 ALERT 证据；`CfSection` 也已订阅 ecoLevel，
「置顶推荐」左侧橙条就是档位色）。真正缺的是**卡片元素不参与情绪**：
分类色标固定 `ArticleCat.bg(category)`（四类永远薄荷/青/蓝/珊瑚），
于是「背景在报警、色标还是绿的」，情绪表达被割裂。

**新增 `EcoTheme` 情绪可视化 API**（碳情绪可视化的唯一入口）：
- `tintByMood(base, blend, ratio)`：颜色插值（自带 parseColor）
- `moodStep(level)`：档位基准强度（alert 0.55 / warn 0.30 / none 0.10 / eco,good 0）
- `moodColor(level)`：情绪色（alert→Accent.FOOD / warn→Accent.ENERGY）
- `moodTint(level, base, rank)`：**按分类分档**混合

**⚠️ 回测推翻了自己的初版（重要）**：
初版对四类用**同一个 ratio**，实算发现**档位越高四色越趋同**：
warn 最小两两色差 6、alert 仅 **4** —— 四类在 ALERT 全变成同一种脏粉，
「这是哪一类」的信息编码被抹掉，情绪可视化目的反而落空。
根因：四个分类底色都是**极淡的同调浅色**（淡青/淡蓝/淡绿/淡黄），
等量混合到同一暖色后差异必然被压平。

改为**按 rank 分档**（以「政策(青)→生活(黄)」为情绪梯度，冷色移动少、暖色移动多）：
`graded = step * (0.55 + rank*0.22)`。
ALERT 档实测：政策 #E5D4D2 / 基础 #E7C5C5 / 技巧 #E6BBAF / 生活 #EEAD9E，
最小色差回到 **30（可区分）**，同时整屏明显偏珊瑚。

**踩坑**：`Theme.ets` 原本**零 import**。想复用 `GlassLight.rgbaOf` 会形成
**循环依赖**（GlassLight 已 import Theme）→ 就地实现一份 `parseColor`，
只支持 `'#RRGGBB'` 与 `'rgba(r,g,b,a)'` 两种写法。

**应用点**：`ArticleListPage` 的图标底(154)与分类徽章(188)改走 `moodTint`。
置顶 Hero 渐变、PinnedCard、Section 色条原本就跟随档位，未动。

**构建**：BUILD SUCCESSFUL（29s，0 error）。

**方法论沉淀**：
1. **对比度必须连背景一起量**，且要问「这个背景是固定的吗」——
   本例文字色没错、背景随碳情绪变了，**次级色令牌假定了中性底**。
   「部分页面/部分档位才看不清」优先怀疑背景非中性。
2. **情绪可视化不能抹掉信息编码**：分类色要"带情绪"而非"换成情绪色"，
   且混合系数要**按色相分档**，否则高强度下所有类别趋同。
3. 设计改动后**先脚本回测再交付**：本轮两次靠回测抓住自己的设计缺陷
   （placeholder 3.60:1、moodTint 色差 4）。
4. 用户问「要不要改成 X」时，先给**理由**再给方案 —— 本例"变白"直觉上对，
   实则会破坏层级与噪音控制，提亮到 5.39 才是正解。

## 深色模式「我的/看板」仍是浅色（themeTick 订阅漏了两层）

**用户诉求**：「深色模式只有记录和科普达到预期效果，我的和看板显示与记录科普显示效果不一致」
（附科普页截图=正常深色；我的页截图=仍浅色，顶部安全区深、正文浅）。

**根因一：页面根容器没订阅 themeTick**（表现：整页底色不换）
`MinePage` / `DashboardPage` 的 `.backgroundColor(EcoTheme.bgSolid(...))`
挂在 **Scroll** 上，而 themeTick 的读取钩子只写在 Scroll **内部的 Column**
（MinePage:248 / DashboardPage:291）。
`Theme.ets` 色值是 static 字段**不响应**，换血后只有**订阅了 themeTick 的组件**
才重建 —— Scroll 自身没订阅 → **底色停留在建页那一刻的浅色值**。

截图特征完全吻合：顶部安全区深色（Index 根层订阅了）＋ 正文浅色（本页根没订阅）。

**为什么记录/科普正常**：它们的**条目**（RecordDayItem / ArticleCard）额外订阅了
themeTick（RecordListPage:90,125,199 / ArticleListPage:125,199,213），
条目重建把父级一起带上；MinePage / DashboardPage 的条目没有这层订阅。

**根因二：8 个共享组件漏订阅**（表现：条目内容不换色）
`Components.ets` 里只有 `CfCard` / `CfTopBar` / `CfGlassDisc` 订阅了 themeTick，
**`CfPill` `CfCatBadge` `CfSection` `CfEmpty` `CfStatTile` `CfProgress`
`CfButton` `CfListRow` `CfSwitchRow` `CfCloseBtn` 全部没订阅** ——
它们读 `Neutral.CARD` / `Neutral.TEXT` / `Glass.DISC_BG` 等 static 值，
不重建就一直拿旧色。所以「我的」页条目在深色下仍发浅。

**修复**：
① MinePage / DashboardPage：把 `.opacity(this.themeTick >= 0 ? 1 : 0)`
   补到 **Scroll 根容器**上（值恒 1，无视觉影响，只为触发重建）。
② `Components.ets`：给上述 **10 个组件**各补
   `@StorageProp('themeTick') private themeTick: number = 0`，
   现 **13/13 组件全覆盖**（awk 脚本可一键核查）。
③ `CfCloseBtn` 的注释「留空则每次 build 现取（响应深色换血）」此前是**空头承诺** ——
   不订阅 themeTick 就不会重新 build，补订阅后注释才成立（已在注释里点明）。

**构建**：BUILD SUCCESSFUL（44s，0 error）。

**方法论沉淀（核心）**：
1. **static 色值 + 不订阅 = 永远不换肤**。凡是「build() 里读 Theme.* 的组件」，
   都必须有 `@StorageProp('themeTick')`；少一个就深色漏一块。
   核查脚本：`awk '/^export struct Cf/{name=$3;has=0}/StorageProp\(.themeTick.\)/{has=1}/^}/{print name,has}'`
2. **themeTick 钩子必须挂在「挂着背景色的那个组件」上**，不是挂在它的子节点上。
   本轮根底色挂在 Scroll、钩子挂在内部 Column → 页面白了一整天。
   症状识别：外层（安全区/根 Stack）已换色、只有页内浅 ⇒ 页内根没订阅。
3. 页面能显示 ≠ 页面能换肤。**「部分页面深色正常」时优先怀疑订阅覆盖率不一致**，
   而不是继续调色值（色值是对的，是压根没重新读）。

## ⚠️ CfStatTile 修复的回归 + 全库统一修正（MinePage 塌成色带）

**用户诉求**：「我的页面出现UIbug」（截图：进度条卡挤到顶部、两条色带垂到底、宫格内容全没）。

**这是我上一轮修复引入的回归，必须记住：**

上一轮修「三宫格只显示一张 + 右侧多出一条边」时，我在 `CfStatTile` 根 Column 上
加了 `layoutWeight(1)` + `width('0%')`，以为这样就能在 Row 里均分。

**错在：ArkUI 的 `layoutWeight` 按「父容器主轴方向」生效，没有「只对某轴加权」。**
- 父是 Row   → 主轴水平 → 均分宽度 ✅（RecordListPage 想要的）
- 父是 Column → 主轴垂直 → **子节点被纵向拉伸** ❌

而本组件的通用用法是 `Row > Column().layoutWeight(1) > CfStatTile`
（MinePage / BackupManagePage 等 10+ 处都这么写），此时 tile 的直接父容器是
那层 **Column** → `layoutWeight(1)` 让它纵向撑满 → 四宫格塌成两条垂到底的色带、
内容全被挤没。截图即此现象。

**正确解法（ArkTS 没有「只对某一轴加权」的 API）**：权重必须加在**包裹层**，
组件自身只保留 `width('100%')`：
```
Row({ space }) {
  Column() { CfStatTile({...}) }.layoutWeight(1)   // 权重在包裹层
  Column() { CfStatTile({...}) }.layoutWeight(1)
  Column() { CfStatTile({...}) }.layoutWeight(1)
}
```
组件已回退为 `.width('100%')` 并删除 `weight` 参数（不留半吊子开关）。

**全库审计（11 个页面 / 33 处同款 bug）**：脚本比对每个 `CfStatTile` 前一行
是否已是 `Column() {`：
- MinePage(4) / BackupManagePage(4) / RecordListPage(3)：原本就有 Column 包裹 ✅
- **11 个页面 33 处是裸放 Row** ❌ 同款溢出：
  CategoryAnalysis / TrendChart / LevelTree / BadgeWall / PointsHome /
  PointsMall / PointsRecord / TaskCenter / ExportReport / Family / MonthBill
  （都是同一种 `StatRow()` 形状，故可脚本统一处理）

**批量改写方式（可复用）**：Python 脚本用**括号配对扫描**（非正则）定位每个
`CfStatTile({...})` 块 → 包成 `Column(){...}.layoutWeight(1)` → 按原缩进重排。
ArkTS 对象字面量里花括号极多，正则极易匹配错位；脚本须跳过字符串字面量与行注释。
显式 `encoding='utf-8'` 读写（**绝不能用 PowerShell 改含中文的文件**）。
改前备份 pages 目录、改后 build 验证。共 33 处，BUILD SUCCESSFUL（45s）。

**方法论沉淀（重要）**：
1. **ArkUI layoutWeight 按父容器主轴生效** —— 给「可能被放进 Row 也可能被放进
   Column」的组件加 layoutWeight 是**危险的**：Row 里均分宽度（好），
   Column 里纵向拉伸（塌）。公共组件的权重应由**调用方包裹层**承担。
2. 改公共组件前必须 grep 全库调用点，确认没有哪种用法会被新参数破坏；
   本轮没审计才造成回归。
3. 「同一形状的 bug 出现在 N 个页面」→ 优先脚本批量修（33 处人工必错且慢），
   改前备份 + 改后 build。
4. 用户报「某页面 UI 坏了」时先判断是否**上一轮改公共组件的回归** ——
   本例真凶就是我自己的上一轮改动。

## 液态玻璃通透度整改（对齐苹果 Liquid Glass，两套独立参数表）

**用户诉求**：不够通透；光的位置变了（应从左上 45° 进入）；深色数值还原之前，浅色再改。

**苹果官方口径（靶值参照）**：染色层浅 8–14% / 深 20–28%；1px 内描边浅白 22% / 深白 8%；

① ArkUI `backdropBlur(radius, BlurOptions)` 的 `BlurOptions` **只有 grayscale**，
   全 SDK 无 ColorFilter / RenderEffect → **拿不到饱和度提升**；
   且 card 档为性能红线永不挂模糊 → 染色层必须比苹果更实，0.72 是浅色可读性底线。
② 折射/色散声明式无法表达，改用「边缘亮带 + 背光内阴影」近似。

**改动（ui/GlassLight.ets + ui/Theme.ets + ui/GlassSurface.ets）**：

1. **深色全部还原**到改动前：washAlphaDark pill 0.05→**0.10**、
   edgeAlphaDark pill 0.56→**0.68**、innerAlphaDark pill 0.12→**0.16**、
   edgeBorderDark pill 0.50→**0.62**。
2. **浅色染色层是主因**：card 0.86→**0.72**（0.86 几乎等于不透明白板）；
   pill 0.46→0.42，panel 0.55→0.50。Theme.ets 里 `applyLightValues()` 与
   `Glass` 类字段初值**两处都要改**（初值用于未调 ThemePalette 的路径）。
   EDGE 0.75→0.52、HIGHLIGHT 0.72→0.60（死白描边是「发光边框」观感的来源）。
3. **入射感**：`washColors` 高光停靠点从 `0/0.38/0.62` 改为
   `0 → 0.12(峰) → 0.38 → 0.55 全归零`。原来一路铺到 62% 是「整片玻璃均匀染色」，
   没有入射感；现在中段全透明，中央留给背景透射 —— 这才是通透感的真正来源。
4. **接触纱不能平铺**（通透度头号元凶）：原先全幅 `rgba(12,18,16,0.14)`，
   等于给白玻璃蒙灰。新增 `GlassLight.scrimColors()` 返回 135° 定向渐变
   （左上透明 → 右下压深），`GlassLightLayers` 改用 linearGradient；
   强度 0.14/0.07 → 0.10/0.05。
5. 浅色光照参数收一档：wash 0.12/0.15→0.11/0.13、edge 0.36/0.42→0.30/0.34、
   inner 0.06/0.08→0.05/0.07、edgeBorder 0.56/0.62→0.46/0.52。

**通透度三原则（可复用）**：
① 染色层是主因（不是高光）；② 接触纱必须定向不能平铺；
③ 厚度归厚度 —— 由1px 背光描边 + 内阴影建立，不是靠把面纱调亮，
面纱越亮越闷，通透度与厚度此消彼长。

**SDK 能力结论（常备查）**：`backdropBlur` 第二参 `BlurOptions` 仅 `grayscale:[n,n]`；
全 SDK 无 ColorFilter / RenderEffect / 饱和度 API —— 想做 saturation boost 走不通。

## 分类 chip「选中哪个哪个看不清字体」（LinearGradient 停靠点重复）

**现象**：科普页分类栏，选中任一 chip（气候变化/双碳政策…）文字看不清。

**像素取证**：截图 817×920，chip 行 y=183，选中 chip 底色 `(253,255,254)` / `(252,254,253)` /
`(246,254,252)` —— **纯白，无一丝绿意**；未选中 chip 是 `(239,251,247)`。
选中态本应是品牌实底 + 白字，实际是「白底 + 白字」，故完全不可读。

**根因**：`GlassLight.pillSurface()` 合成渐变时停靠点**重复**：
`colors.push([base, 0])` 占位置 0，而 wash 段位置 `wash[i][1] * 0.7` 中 `wash[0][1] = 0`
→ 映射后仍是 0，与首点重位。
ArkUI `LinearGradient` 要求停靠点**严格递增**，遇到重复位置整条渐变失效并退回纯白。
未选中态恰好也退化成白玻璃，肉眼看不出异常 → bug 长期潜伏。

**修复**：
1. wash 区间收进 `[0.02, 0.90]`（`LO=0.02, SPAN=0.88`），保证 `0 < 0.02 < … < 0.90 < 1` 严格递增。
2. `ArticleListPage.FilterChip` 的 `activeBg` 从 `EcoTheme.primary`（ECO_TO #3FBF9F，
   白字对比度仅 ~2.2:1）改为 `EcoTheme.primaryDeep`（#2A9E82，~3.9:1）配 Bold 字重。

**教训（ArkUI 渐变）**：自建 `LinearGradient` 合成多段光照时，停靠点必须校验严格递增；
只要某段原始位置是 0，线性映射（如 ×0.7）后仍会与 base 的 0 重位，
整条渐变**静默失效退回纯白** —— 不报错、不告警，只能靠像素取证发现。

**构建注意**：输出里出现 `BUILD SUCCESSFUL` 时，PowerShell 工具仍可能报 exit code 1
（管道末`Select-String` 无匹配返回非零），以输出文本为准，不要误判为构建失败。

## 二、开屏页「一触青绿」消失 —— 我上一轮的错误修复

### 现象
用户反馈开屏页不见，**并明确指出我上一轮的分析不对**（调成 2 秒依然不出现）。

### 我错在哪
上一轮我把根因归为「onPageShow 首次创建即触发，把 showSplash 秒关」——

用户把时长调到 2 秒仍无显示，说明问题与时长无关，我本应立刻转向别处。

### 真正的根因：是我上一轮引入的回归
上一轮为实现"淡入动画"，我加了：

2. 把 `.opacity()/.scale()/.animation()` 从 `if` 块内移到 **Navigation（主体内容）** 上 ——

1. **初始透明度/可见性相关的属性，初值绝不能是"不可见"**。

2. **装饰性属性要加在正确的层级**。我上一轮把 opacity 加在 `if` 块之后，

3. **用户反馈与我的结论冲突时，先验证我的结论**。

→ 沉淀：Previewer 调试时，凡依赖生命周期的逻辑都要有

## 三、修复：进「建议」页即崩溃 —— MockStore 无限互调爆栈

### 现象
用户一进「建议」页 App 直接崩溃，日志：
```
RangeError: Stack overflow!
  at overview entry (MockStore.ets:321:43)
  at badges entry (MockStore.ets:482:41)
  at overview entry (MockStore.ets:347:29)
  ... 无限交替
```

### 根因：两个静态方法互调成环
```
overview() 第 347 行 → MockStore.badges()   （统计 badgeCount）
badges()   第 482 行 → MockStore.overview() （取 totalKg/recordCount/treeCount）
```
谁先被调用都会死循环。外部入口是 `DataSource.shareText()`
→ `MockStore.shareText()` → `overview()`。
崩溃栈里 `at overview (321:43)` 其实是旧行号 records() 一帧，
真正闭环是 347 ↔ 482。

### 修复：badges() 不再依赖 overview()
徽章判定只需要 4 个指标，改为从 `records()` 现算，口径与 overview() 一致
（totalKg 同样 Math.round(x*100)/100，continuousDays 同样硬编码 12，
treeCount 同样 Math.floor(totalPoints / POINTS_PER_TREE)）。
`overview()` 保持原样继续调 `badges()` —— 环从被调方根部打断，
两个方向的调用链（shareText/members → overview → badges → records）都终止。

### 沉淀
1. **静态工具方法之间画调用图再动手**。本次 `MockStore` 有 20+ 个静态方法，
   只用 grep `MockStore\.\w+\(` 一遍就定位了全部 4 处 overview/badges 调用点，
   10 分钟闭环；没有这个清单就会在 1200 行文件里盲猜。
2. **「统计型」方法最容易互调成环**：overview 想要 badges 的数量，
   badges 想要 overview 的总量 —— 双方都以为对方是"只读数据源"。
   防办法：派生指标只从最上游的原始数据（records）算，不跨统计层引用。
3. ArkTS 里 `RangeError: Stack overflow` 的栈会**反复打印同一组帧**，
   看到两组帧交替出现 = 互调环，一组帧重复 = 自身递归。

验证：hvigor BUILD SUCCESSFUL in 27 s 916 ms（build-check.ps1 被执行策略禁用时，
可内联等价命令：设 JAVA_HOME/PATH 后 node hvigorw.js assembleHap --no-daemon）。

## 五、二级页面进入时：底部胶囊「直接消失」→ 滑向＋钮缩放消失

### 现象
用户截图（一级页 + 底部胶囊）：「进入二级页面这里的消失动画太简陋了，
像是直接消失……能不能让他向右消失，在加号处消失」。

### 根因：visibility 秒切 + Blank 不占位（两个叠加 bug）
1. 胶囊显隐挂的是 `.visibility(this.onSubPage ? None : Visible)` ——
   visibility **不是可动画属性**，一翻转组件当场退出渲染，所以「直接消失」。
2. 左侧占位 `Blank()` **没给 layoutWeight**（ArkUI Blank 默认 0 尺寸、不占位）——
   胶囊退出布局后，右侧「＋」钮**从右端跳到左端**。两个 bug 叠加，
   进子页面时就是「胶囊凭空没了 + 加号甩到左边」，非常简陋。

### 修复（Index.ets）
- 新增退场三件套状态 `capsuleShift / capsuleScale / capsuleAlpha` +
  延迟移除标志 `capsuleGone`（动画播完才 visibility，提前切一帧都看不到）
- `syncStackState` 拆出 `animateCapsule(deep)`：
  · 退场：`translateX = barW/2 + 38`（胶囊半宽 + 10vp 间距 + 28vp 钮半径，
    中心正好落进＋钮中心）+ `scale 0.12` + `opacity 0`，360ms EaseInOut
  · 返场：先 capsuleGone=false（以旧缩小态 invisible 回到布局），
    再 animateTo 展开到 shift 0 / scale 1 / alpha 1
- 占位 Blank 改挂 `capsuleGone` 并补 `.layoutWeight(1)`：
  **必须晚于胶囊退场**才出现，否则会和还在动画的胶囊瓜分剩余宽度、瞬间瘦一半
- 常量 CAPSULE_ANIM_MS=360 / CAPSULE_EXIT_SCALE=0.12 提为模块级

### 沉淀
1. **visibility 不能做退场动画**。要「消失得有动画」，路线只有一条：
   动画属性（translate/scale/opacity 都不参与布局）跑完 → 再切 visibility。
   本 SDK 的 `animateTo` 签名**没有 onFinish**（查了 @ohos.arkui.UIContext.d.ts，
   只有 `animateTo(value, event)` 两参版），收尾只能用**同 duration 的 setTimeout**。
2. **「向右消失 + 在加号处消失」的数学**：位移量 = 自身半宽 + 间距 + 目标半径，
   缩放绕中心，两者同步补间，中心轨迹就落在目标圆心。translate/scale 不触发
   布局，动画期间「＋」钮不会被挤动（这是选它们而不是改 width 的原因）。
3. **占位件出现的时机**：Blank 早一步 layoutWeight 会和动画中的本体瓜分空间。
   凡是「A 动画退出、B 占位接手」的戏码，B 必须等 A 的 visibility 真正置 None 后。
4. 查 API 不要凭记忆：这次先翻了 SDK 里 nav_destination.d.ts（customTransition
   是 @since 15 且需要 NavDestination 包裹，本项目 PageMap 返回裸页面用不了），
   又翻了 blank.d.ts（Blank 默认 0 尺寸）和 UIContext.d.ts（animateTo 无 onFinish），
   全部有据可依才动手。

验证：hvigor BUILD SUCCESSFUL in 23 s 349 ms。

## 六、沉浸式底部：玻璃条下要有内容 + Tab 药丸动画顺滑化

### 需求（用户原话）
「他地下那层底色换成纯透明，因为上层按键是液态玻璃，这样才可以体验出效果，
而且她四个页面切换的胶囊动画并不流畅」

### 需求一：玻璃条下面是平板色 → 内容从玻璃下穿过
**根因**：内容层 Column 尾部有个 76px 占位 Blank + Column 自身半透明底，
玻璃条永远坐在一块**平色面板**上。backdropBlur 采样平色 = 模糊个寂寞，
液态玻璃看起来就是半透明白药片——**没有内容可模糊，效果永远出不来**。

**修法**（Index.ets + 3 个页面）：
- 删掉 76px 占位 Blank、删掉 Column 的 `.backgroundColor(EcoTheme.bg())`
  —— 内容层不再铺底色，四个一级页 Scroll 直接铺到屏幕底
- 三个页面 Scroll 的 bottom padding 30 → 96（RecordListPage 原本就是 96）：
  滚到底的余量从「占位 Blank」搬进「页内 padding」，最后一张卡仍能滚出玻璃条
- 根层 Stack 的 `bgSolid` 实色**保留**：它是页面底色， Literally 全透明会露出
  系统白（就是两轮前「底部发白」那个 bug 的回归）。用户说的「透明」=
  不要平板面板、要透出内容，已按此实现

### 需求二：药丸动画不流畅 → 药丸先滑，内容后切
**根因**：旧 `switchTab` 在同一个 animateTo 里改 `currentTab` ——
药丸滑动（200ms）与**整页重渲染**（Dashboard 全是卡片/渐变/模糊）挤在同一批帧，
主线程被页面构建占满，合成层动画跟着掉帧。附带问题：文字高亮动画 620ms
与药丸 200ms 严重脱节（药丸到了半天高亮才追上）。

**修法**：
- 新增 `@State pillIndex`（药丸/高亮位置）与 `currentTab`（内容）**解耦**
- `switchTab` 拆两步：① 立即 animateTo 改 pillIndex（纯合成层，主线程空闲，
  300ms EaseInOut）；② setTimeout(300ms) 后才切 currentTab（页面此时才构建）
- TabCell 高亮（fontWeight/fontColor）改挂 pillIndex，动画时长同步 300ms
- `tabSwitchTimer` 连点即清，内容永远跟着最后一次点击
- TAB_ANIM_MS=300 提为模块常量

### 沉淀
1. **液态玻璃的三件套是「半透明底 + backdropBlur + 下层有内容」**。
   前两件项目早就做了，第三件一直被占位 Blank 挡着 —— 玻璃区下必须是
   可滚动内容，不能是纯色面板。这也是判断「玻璃有没有白做」的硬标准。
2. **指示器动画和重内容切换不要同帧**。先滑指示器（合成层）后切内容，
   是 Tab 类交互的通用解法；本次掉帧根因就是两者抢主线程。
3. 底部沉浸式（内容延伸到悬浮条下）时，余量要从「外层占位」搬进
   「页内 Scroll 的 bottom padding」——占位 Blank 会掐断玻璃的内容来源。
4. 用户说「换成纯透明」时要想清楚 transparent 到哪一层：透到系统白就是回归，
   透到页面内容才是他要的效果。**问「透明给你看什么」比直接设 rgba(0,0,0,0) 重要。**

验证：hvigor BUILD SUCCESSFUL in 29 s 513 ms。

## 七、Tab 切换：药丸与主页面同步滑动（同时开始同时结束）

### 需求（用户原话）
「点击下方四个按钮，药丸动画开始滑动时，上面主页面也增加动画，同时开始滑动，
做到动画同时开始同时结束」（底部玻璃效果已确认做好）。

### API 调研结论（先查后改，全部有据）
1. **`Tabs.customContentTransition(delegate)`**（@since 11）：delegate 签名
   `(from, to) => TabContentAnimatedTransition`，返回 `{timeout?, transition(proxy)}`；
   proxy 只有 `from/to/finishTransition()`，**没有页面节点句柄** —— 页面位移靠
   共享状态（官方示例：transition 回调里直接赋值起始帧 + animateTo 到结束帧）。
2. **触发方式（关键坑）**：官方文档明确「直接修改 index 跳页时，切换动效不生效」，
   自定义转场**只能由点击页签或 `TabsController.changeIndex()` 触发**。
   → 必须改用控制器驱动，**移除 index 属性绑定和 onChange**（自定义动画期间
   onChange 会延迟到下次切换时补发旧 index，连点时会把 tab 拽回旧值，有害）。
3. **转场期间两页以 Stack 布局叠放**，树序即层序：前进时新页在上（盖上）、
   后退时旧页在上（滑开）——正好都是自然滑动观感，无需手动 zIndex。
4. **`AnimateParam` 有 `onFinish` 字段**（correct 第五节「animateTo 无 onFinish」
   的结论：那是方法签名两参版，参数对象里是有 onFinish 的）。
5. `timeout` 到点自动结束转场（不调 finishTransition 也行）——本方案靠它收尾。

### 实现（Index.ets，全部本地化在这一个文件）
- **一个 animateTo 驱动全部**：`switchTab` 里药丸 translate（读 currentTab）、
  文字高亮（property animation 300ms）、旧页/新页 translate 同一段动画
  → 同帧开始、同时长同曲线、同时结束。`pillIndex` 随之废除，合并回 currentTab
  （内容不再延迟切，解耦失去意义）。
- **页面位移**：四个一级页各包一层全尺寸 Column 挂 `.translate({x: pageShiftN})`；
  `pageShift0..3` 是四个独立 @State —— **@State 数组元素赋值不触发刷新**，
  必须整数组替换或拆独立变量（选了后者）。
- **起始帧/结束帧**：新页先直接赋值 `dir*w` 甩到屏外（官方同款写法），
  闭包里旧页 `-dir*w`、新页 `0`；**旧页不重置起始帧**——连点被上一次切换
  推送中时让它从当前处继续滑离，避免跳变。
- **`contentTransition` 只负责让两页叠放到位移播完**：`{timeout: TAB_ANIM_MS+60,
  transition: 空}`，60ms 缓冲保证 Stack 布局至少活过动画，旧页不会滑一半被收回。
- 宽度来源：包 Tabs 的 Column 挂 `onAreaChange` 实测 `contentW`（与 barW 同模式）；
  `Tabs({controller})` 去掉 index 属性，`changeIndex(index)` 换页。

### 沉淀
1. **「官方说只能由 X 触发」的 API，不要赌属性绑定也行**。这次若继续用
   `Tabs({index})` 属性驱动，自定义转场根本不会触发（文档原话级坑），
   且保留 onChange 会在连点时用延迟补发的旧 index 污染状态。
2. **同步多元素动画的最稳写法：全部目标值进同一个 animateTo 闭包**，
   起始帧用直接赋值（闭包外）。属性级 `.animation()`（文字高亮）与 animateTo
   只要同时长同曲线且由同一次状态变更触发，同样严格同步。
3. 滑动转场不必自己写双层 Stack：`customContentTransition` 的 Stack 叠放 +
   页面内 wrapper translate，既保留 Tabs 的页面缓存（Scroll 位置不丢），
   又是纯合成层动画（页面不重建，主线程空闲）。
4. 构建入口备忘：hvigorw.js 在 `DevEco\tools\hvigor\bin\hvigorw.js`，
   工作目录是 `D:\11\carbon-master\app`（不是仓库根）。

验证：hvigor BUILD SUCCESSFUL in 27 s 178 ms（无 ArkTS ERROR/WARN）。

## 十七、统一玻璃光照模型（GlassLight + GlassSurface，全库唯一定义）

用户要求「液态玻璃具备统一、真实、可读的光照模型，而不是简单高光贴图」，
列出 9 项必须项（全局光源/环境光/菲涅尔/高光形状/折射近似/内外阴影/
动态交互/可读性/性能降级）。全部落地：

- **新文件 `ui/GlassLight.ets`**（光照模型唯一定义处，纯静态类）：
  · 主光源 = 左上 45°（linearGradient angle 135，全库唯一）；
    派生：顶边受光 180°、左边受光 90°、外投影 offsetX/offsetY 均 >0。
  · 环境自适应 `luma()`（Rec.709 加权，解析 #hex 与 rgba）→ `adapt()`：
    亮底 ×0.82 防过曝、暗底 ×1.22 防发灰；card 档 tint 只微调 ±0.02

    innerA 0.10/0.07/0.09（pill/card/panel，均 ×adapt）。
  · 降级 `GlassQualityLevel`：CINEMATIC/BALANCED(默认)/LITE

## 底部白条（系统导航区露底）修复 —— 两次误判的教训

### 现象
屏幕最底部一条纯白 #FFFFFF 带子。用户报告记录页、科普页有，
「我的」「主页」正常。

### 误判一：以为是页面 bug
先怀疑记录/科普两页的根节点（它们用 List + layoutWeight，
而正常的我的/主页用 Scroll + height('100%）），
并据此回退了 EntryAbility 的窗口层改动。**方向完全错了。**

### 误判二：expandSafeArea 不够就以为是别的问题
上一轮已加过 `expandSafeArea([SYSTEM], [BOTTOM, TOP])` 但白带仍在，
于是转去找「为什么只有这两个页面异常」。

### 真相：像素取证 + 用户描述都不完全可靠
对**主页那张「正常」截图**做同样的像素扫描，
结果 y=804~830 同样是纯白 (255,255,255) —— **主页也有白带**，
只是全屏尺寸下被底部导航盖住、不易察觉。
用户的「主页正常」是视觉印象，不是事实。

**所以这是全局问题，与页面无关。**

### 关键认知：只加 expandSafeArea 治不了
`expandSafeArea` 只让组件的**绘制区域**延伸进安全区，
但**系统导航条本身仍是不透明的**，会照旧盖在根底色上。
必须在**窗口层**把系统栏背景设为透明：
```ts
windowStage.getMainWindow().then((mainWindow: window.Window): void => {
  mainWindow.setWindowSystemBarProperties({
    statusBarColor: '#00000000',
    navigationBarColor: '#00000000'
  })
})
```
必须放在 `loadContent` **之前**，否则首帧闪一下白。

### ⚠️ 踩坑：别设 contentColor
`statusBarContentColor` / `navigationBarContentColor` 控制的是
系统栏**图标颜色**（时间/电量），不是背景色。
设成 `#00000000` 会让图标整个消失。
背景透明后图标由系统按底色亮度自适应，故一律不传。

### 方法论教训（重要）
1. **用户对「哪些页面有问题」的描述可能是视觉印象，不可当事实。**
   本次用户说「我的和主页正常」，像素扫描证明主页同样有问题。
   遇到「A 页有问题、B 页正常」时，**必须先扫描 B 页取证**，
   再决定是否需要按页面差异排查 —— 否则会顺着错误前提做无效改动。
2. **「改了没效果」先质疑方案层次，而不是急着换页面。**
   expandSafeArea 属于组件层，治不了窗口层的系统栏底色。
   层级不对时，怎么调参数都没用。
3. 判断「这块颜色属于谁」：像素值是否精确等于某主题令牌。
   纯白 #FFFFFF 不等于任何令牌（浅色根底是 #FBF8F3）→ 必然来自系统/窗口层。

**现象**：用户截图深色模式下页面底已变深，卡片仍是浅灰白 `(225,224,222)`。

**根因（重要范式）**：ArkTS `@Component` 的**普通成员字段初值只在组件构造时求值一次**。
`bgColor: string = Glass.CARD_BG` 里的 `Glass.CARD_BG` 是 static 字段，
`ThemePalette.applyDark()` 重新赋值后**不会回灌到已存在的组件实例**。
凡是「成员字段直接持有一枚主题色」的写法，深色模式下必然局部不换肤。

**修复口径**：一律改成「留空 + 私有方法现取」：
```ts
bgColor: string = '';
private bgValue(): string {
  return this.bgColor.length > 0 ? this.bgColor : Glass.CARD_BG;
}
// build() 里 .backgroundColor(this.bgValue())
```
显式传参的调用方（如 `CfCard({bgColor: Glass.PANEL_LIVE_BG})`）在父组件 build 时求值，
父组件订阅了 themeTick 会重建，因此天然正确。

**本轮改造清单**（`ui/Components.ets`）：`CfCard.bgValue`、`CfCatBadge.bgValue/fgValue`、
`CfStatTile.accentValue/tintValue`、`CfProgress.trackValue`、`CfCloseBtn.colorValue/bgValue`、
`CfListRow.rightColorValue`；`pages/mine/MinePage.ets` 的 `MineEntry.rightColor` 默认值改 `''`。
全部显式传参处（BadgeDetailSheet / QuizSheet 传 `Glass.PANEL_LIVE_BG`）保持不变。

**教训（编辑事故）**：用 `python` 批量 `s.replace("Neutral.TEXT_SUB)", "')")` 想改默认值，
误伤了同文件 11 处 `fontColor(Neutral.TEXT_SUB)` 与 `new MineEntry(..., Neutral.TEXT_SUB)`，
编译报 11 个 Unterminated string literal。
→批量替换必须带上下文锚点，且替换后立刻 grep 回验，绝不能只看目标行。

## 全局光照统一：全库 135° 左上 45° 入射（含二三级页面卡片）

**用户诉求**：「液态玻璃做全局修改，都要左上角 45° 射入，包括二级三级菜单内的卡片」。

**根因（全局性，不是某几处）**：
`GlassLight.LIGHT_ANGLE` 本身早就是 135°，但**大量玻璃面根本没接光照模型**——
全库扫描统计：
- `CfCard` **47 处**（分布 25 个页面，含几乎所有二三级页面）走的是
  `.backgroundColor(Glass.CARD_BG)` **纯平涂**，无光照层、无 135° 渐变；
- `GlassPanel`（有完整光照栈）只有 **5 处**，`GlassPill` 只有 **2 处**；
- `CfTopBar` / `CfGlassDisc` / `CfCloseBtn` 玻璃分支同样平涂；
- 另有 12 处在页面里**手写**玻璃容器绕过 CfCard（`Glass.CARD_BG` / `PANEL_LIVE_BG` /
  `SEGMENT_TRACK_BG`）。

即：一级页面（走 GlassPanel）有光照，点进二级页面卡片就没了 → 用户感知「光的方向变了/没了」。

**方案**：新增 `GlassLight.surface(base, tier, ambient, gloss)` —— 把
**底色 + 左上白光 + 右下内阴影压进一条 135° 渐变**，零子层直接铺在元素自身。
`pillSurface` 改为它的别名（行为不变）。

**为什么单层就够**（建立 45° 入射观感的三件事同在一条对角轴）：
① 左上白光（washColors 起点=受光面）② 右下深内阴影（终点=背光面/厚度）
③ 1px 四边异色描边（上/左亮、下/右深）。顶/左菲涅尔只是该轴的边缘加强，
卡片尺寸上肉眼不可辨，省掉换来全库 40+ 处卡片**零离屏合成**开销。

**落地清单**：
- `GlassLight.ets`：新增 `surface()`；`pillSurface()` 转为别名转发。
- `Components.ets`：`CfCard`（47 处）双分支均改 `.linearGradient(surfaceValue())`，
  描边改 `borderColors(CARD)`、投影改 `shadowOf(CARD)`；新增 `ambient` 参数 +
  `glassSurfaceValue()`；`CfTopBar`/`CfGlassDisc`/`CfCloseBtn` 玻璃分支走 PILL 档统一。
- 12 处页面手写容器改 `linearGradient(GlassLight.surface(...))`：
  RecordListPage×3、TrendChartPage×3、BadgeWallPage、LevelTreePage、
  BehaviorAddSheet×2、CategoryAnalysisPage、SuperTerminalPage、BadgeDetailSheet；
  为 8 个文件补 `GlassTier` import（6 个插入到最后一条 import 后，2 个替换已有锚点）。
- **刻意不动**：`CfPill`（成功/警告/危险等**语义色**标签，不是玻璃）；
  `SplashPage`、`EcoDebugSheet`、各 `angle: 90/135` 的品牌色按钮/图标/折线
  —— 那些是有意的品牌渐变与图表绘制，不属于玻璃光照层。

**口径沉淀**：
「统一光照」不等于「把角度都改成 135」——要先分清**玻璃光照层**与
**品牌色渐变/语义色/图表绘制**三类，后者有自己的方向语义，不能强改。
真正要查的是「哪些玻璃面压根没接光照模型」，那才是光方向不一致的根因。

## 底部导航「白条」终局修复：平涂底色把光照层盖住（两层打架）

**用户诉求**：参照主页的代码，把记录/科普页液态玻璃下的白条改为透明。

**取证（新截图 449×194，深色模拟器记录页，选中「记录」）**：
```

胶囊左上 (250,255,254)   ← 很白
胶囊右下 (211,220,217)   ← 很脏
胶囊下沿 y=136 结束；y=138~178 全是页面底色（无纯白色块）
```
**仍然不存在纯白条**。白条 = 胶囊自身的平涂观感。

**根因（本轮新发现，口径性错误）**：
底部胶囊 / 滑动药丸 / 圆钮三处都是「**平涂底色 `.backgroundColor()` + 底下垫 `GlassLightLayers`**」
—— 而平涂是**不透明**的，把底下那层 135° 光照栈**整个盖住**，
两层不但没叠加出效果，反而只剩平涂观感（左上很白、右下很脏）。
这与「CfCard 没接光照」是**两个不同方向的同类错误**：
一个该接没接，一个接了但被平涂盖住。

- 三处的 `GlassLightLayers(...)` **全部删除**（单层合成后再叠 = 高光与内阴影两倍、发脏）
- 清理 `Index.ets` 的 `GlassLightLayers` import（已无引用）

**口径沉淀（重要）**：
① **玻璃面只能选一种光照承载方式** —— 要么自身 135° 合成渐变（`surface()`，
   零子层、fit-content 安全），要么叠 `GlassLightLayers`（100%×100% 多层）；
   **绝不能「平涂底色 + 光照层」**，平涂不透明会盖掉光照层。
② 改这类问题时先扫 `.backgroundColor(Glass.*)` 与 `GlassLightLayers` 是否**同现**。
③ 取证脚本复用：`/tmp/probe2.py`（自写 zlib + 五种反滤波 PNG 解码，

## 底部胶囊透明化：白度不是光照问题，是染色层浓度问题

**用户原话**：「我让你修的是这个，他应该是透明的，让胶囊直接在页面之上」。

**结构核实**：胶囊其实**早就是悬浮层** —— `Stack { Navigation(100%), Row{胶囊} }`
alignContent Bottom，Tabs 铺满、内容能穿到胶囊后面（旧 Blank 占位早已移除）。
所以不是布局问题。

**真正根因**：`Glass.BOTTOM_BAR_BG` 浅色 `rgba(255,255,255,0.55)` ——
55% 的白糊在 241,250,247 的浅底上，backdropBlur 糊到的内容完全透不出来，
胶囊就是一条白带。**通透度主因始终是染色层浓度**（苹果口径 8–14%）。

**修复**：`BOTTOM_BAR_BG` 浅色 0.55 → **0.30**（`Theme.ets` 两处：
static 初值 + applyLightValues 换血值）。玻璃感改由 135° 光照 +
1px 四边异色描边建立，不靠刷白。
选中文字近黑（tabActiveColor）+ 未选中 TEXT_MUTED 深灰，
对比度均 4.5:1 以上，可读性不受影响。
PILL_BG（选中药丸 0.42）**保持不动** —— 胶囊变透后，内嵌药丸的白高亮
正是「选中项浮出来」的层次来源，一并降会失去选中态对比。

**方法论沉淀**：用户连续三轮说「白条/透明」，分别是三个不同层的问题：
① 光照档位错（PANEL→PILL）；② 平涂盖住光照层（改 surface 单层合成）；
③ 染色层本身太白（降 alpha）。修一个看一个，每轮取证都成立但都只剥了一层 ——
**「透明感」问题的检查顺序：布局悬浮 → 光照承载方式 → 染色浓度**。

## 「看板能透过胶囊看见内容，记录/科普只能看见一层页面」→ 结构改造

**用户原话**：「在看板这里我可以直接通过胶囊的液体玻璃效果看见下面的东西，
但是记录和科普只能看见一层页面，仿造前面的看板修改」。

**根因（布局结构差异，与玻璃参数无关）**：
- **DashboardPage**：根节点直接一个全屏 Scroll，**所有内容都在滚动流里**，
  滚动中卡片能从底部胶囊后面穿过，backdropBlur 糊出来的是「活的内容」。
- **RecordListPage / ArticleListPage**：`Column { Header(固定) + FilterBar(固定)
  + List.layoutWeight(1) }` —— 头部钉死在顶部，列表只占剩余空间；
  内容结束后胶囊后面永远是空白底色（「一层页面」）。

**修复（仿看板：头部进滚动流）**：
- RecordListPage：Header/Summary/FilterBar 改为 List 的前三个 ListItem；
  非空分支 List `height('100%') + padding { left/right PAGE, bottom 96 }`
  （left/right 必须保留——条目内容不带边距；top 由 Header 内建边距承担）；

**方法论沉淀**：
「胶囊后面没有东西可透」先查**内容能不能滚到胶囊后面**（全屏滚动流），
再查玻璃参数。看板与列表页的观感差异本质是布局结构差异 ——
固定头（Column+layoutWeight）与全屏滚动（根节点直接 Scroll/List）。
⚠️ 拆 Column 根容器时，根上挂的修饰符（backgroundColor/animation/border/
bindSheet）必须逐一迁到新根或分支，否则悬空编译错误。

## 页面根底实色化：半透明底色救不了白底

**用户诉求**：按「根层先钉一层不透明实色底」的思路，修记录和科普页面的导航栏。

**原理**：半透明色只能叠在「已经有颜色」的东西上。Tab 内容层与 Index 根层之间
隔着 `Navigation + Tabs`，若链路上任何一环带系统默认白底，页面那层
`EcoTheme.bg()`（`rgba(242,251,247,0.62)`）就变成 62% 薄荷叠白 ≈ `#F7FDFA`
（99% 是白）—— 整页褪成近白，胶囊的 `backdropBlur` 采样到这层白，
玻璃自然也是白的，液态感全无。

- RecordListPage 两分支根底、ArticleListPage 根 Column、
  MinePage 根 Scroll、DashboardPage 根 Scroll：
  `.backgroundColor(this.ecoBg()/moodBg())` → `EcoTheme.bgSolid(this.ecoLevel)`
  （一级 Tab 四页统一口径）

**口径沉淀**：
① **一级 Tab 页的根底必须不透明**（`bgSolid`），半透明 `bg()` 只能用于
   「已知下方有实色」的场合（如玻璃面内部的 ambient 参数）。
② 根层底色是**唯一来源**，中间层（Navigation/Tabs/TabContent）一律透明，
   不要指望下层兜底。
③ `moodBg()`/`ecoBg()` 在根容器上已无调用点（DashboardPage 的 moodBg
   保留但不再用于根底），后续可清理。
④ 全库仍有 ~20 处二级页面用半透明 `ecoBg()` 作根底 —— 二级页是 NavDestination
   有自己的底色，暂未改；若二级页也出现发白，按同思路处理。

## 底部空白带收缩（用户定位：「胶囊下方到屏幕底边」+「玻璃后只有底色」）

**用户定位（AskUserQuestion 确认，纠正了此前多轮猜测）**：
- 白的位置 = **胶囊下方到屏幕底边**那一段
- 与看板的差别 = **看不到内容，只有一层底色**

**量化根因**：底部空白带由两处间距撑起
- 底部导航 Row `.padding bottom: Space.LG(16)`
- 各页列表 `.padding bottom: 96`
胶囊（高 56）**整块落在列表 96 的空档里** → 玻璃背后必然是空底色。
且 96 远大于胶囊高度 56，滚到底时最后一条内容也停在胶囊上方 40vp。

**修复**：
- `Index.ets` 底部 Row：`padding bottom` Space.LG(16) → **Space.XS(4)**，
  胶囊贴近屏幕下沿，空白带只剩安全区那一圈。
- RecordListPage / ArticleListPage：`padding bottom` 96 → **68**（56 胶囊 + 12vp 呼吸），
  内容能滚到紧贴胶囊下方，磨砂才有东西可透。

**Space 常量备查**：XS 4 / SM 8 / MD 12 / LG 16 / XL 24 / PAGE 18。

**方法论沉淀（重要）**：
「玻璃后面只有底色」的排查顺序：
① 内容**能否滚到**胶囊后面（列表 padding bottom 是否过大 / 滚动区是否铺满）
② 内容**够不够长**（不足一屏时底部必然空白，这是物理限制，代码无解）
③ 底色本身是否发白（实色 vs 半透明叠白底）
④ 玻璃自身染色浓度
⚠️ **不要一上来就改底色**——底色只影响"白不白"，解决不了"透不到内容"。

## 底部导航胶囊「真透明」（BOTTOM_BAR_BG 降浓度）

**用户反馈**：「你只是让白条向下了，不是真透明」—— 收缩 padding / 挪动列表底距只是把空白带走，玻璃仍是一块半透明塑料板。

**根因**：胶囊自身染色层浓度太高。
- 浅色 `rgba(255,255,255,0.30)` / 深色 `rgba(18,25,23,0.62)`
- 无论背后底色是白是黑，染色层够实 → `backdropBlur` 采样到的背景被染色层压掉，玻璃退化。

**修复**（`ui/Theme.ets`，三处必须同改：浅色 static 初值 / `applyLightValues()` / `applyDarkValues()`）：
- 浅色 0.30 → **0.12**
- 深色 0.62 → **0.26**

**依据**：苹果 Liquid Glass 在深色背景上玻璃面几乎不可见，靠**边缘光 + 折射 + 背景内容透出**成立，不靠一层实色。0.26 只够托住文字对比度。

**排查口诀**：「玻璃后面只有底色」→ ① 内容能否滚到胶囊后（列表 padding bottom 是否过大）② 内容是否够长（不足一屏时底部必然空白，物理限制）③ 底色是否发白 ④ 染色层是否过实。④ 与 ①②③ 是独立通道，改 ④ 不影响①。

**构建**：通过（BUILD SUCCESSFUL 22.7s）。

## 滚动视口 padding vs 子节点 padding —— 「记录/科普透不出内容」的真正根因

**用户提问**：「为什么首页和我的就正常，这两个弄不好」。

**根因（结构性，非视觉参数）**：
- Dashboard / Mine：`Scroll { Column().padding({bottom:96}) }` —— padding 挂**子节点**
- RecordList / ArticleList：`List().padding({bottom:68})` —— padding 挂**滚动视口**

**语义差异（ArkUI 关键坑）**：
- padding 挂子节点 → 撑出可滚动溢出区，内容能一路滚到屏幕最底边，穿过胶囊
- padding 挂视口 → 视口本身被压短 68，内容**永远滚不进**胶囊区域，胶囊后面物理上没内容

所以「只看见一层页面」不是玻璃不透明，是 backdropBlur 采到的只有 `backgroundColor` 实色。
**降 BOTTOM_BAR_BG alpha、调玻璃光照层都是白费**，因为背后根本没东西。

**修复**：底部滚动余量从「视口 padding」改为「尾部占位 `ListItem`（height 68）」，视口只保留左右内边距。
- `record/RecordListPage.ets`、`article/ArticleListPage.ets` 各加一个尾部 ListItem

**口诀（加入排查顺序）**：
「玻璃后面只有底色」排查应把 ①② 提前：
1. **内容能否滚到胶囊后面** —— 先查滚动视口上有没有挂 bottom padding（有就是 bug）
2. 内容是否够长（不足一屏是物理限制）
3. 底色是否发白（实色 vs 半透明叠系统白底）
4. 染色层是否过实（alpha）
→ 顺序颠倒是本轮连续改错的直接原因。

**构建**：通过（BUILD SUCCESSFUL 22.0s）。

## 深色模式适配 + 液态玻璃深色重构（结构性，非补色值）

## 碳情绪主题不跟随 —— EcoMoodState.apply() 的无限递归
- 用户反馈「科普页 UI 没随碳行为动态变换」。**注意**：不是缺色值，页面底色本来就取了 `EcoTheme.bgSolid(ecoLevel)`。
- **像素取证是决定性的**：用户截图同一屏内——
  - 置顶卡实底 = 绿色 (70,177,151) → eco 档 `ECO_TO #3FBF9F`
  - 科普页根底 = **(254,243,241)** → 恰好是 `ALERT_SOLID #FDF3F1`（珊瑚警示档）

- **根因**：`EcoMoodState.apply()` 末尾调用 `EcoMoodState.bump()`，而 AppStorage 写入是**同步**的：
  `refresh() → apply() → bump() → 写 ecoTick → 各页 onStorageChange('ecoTick') → EcoMoodState.refresh() → ……`

  - `apply()/refresh()` = 「碳量 → 档位」，写 KEY_LEVEL（响应式，驱动配色）
  - `broadcastDataChange()/bump()` = 「数据变了 → 重新拉数据」，写 KEY_TICK（驱动 load()）

  首页环形进度 `quotaPct()` 取自自己的 `this.ov.todayKg`（load 数据），不依赖信号 → 无回归。
- 修复后 `bump()` 调用点只剩2 处（broadcastDataChange + LocalStore:242），`apply()` 只有 1 个调用者 → 递归链彻底断开。

## 深色模式「没有适配」—— ThemeMode.init() 的静默 catch 吞掉整段换血
- 用户反馈「深色模式没有适配」并附「我的」页截图。**先做像素取证**再动手：
  - 页面底实测 (241,250,247)，精确等于浅色套值 `ECO_SOLID #F2FBF7`=(242,251,247)
  - 而深色套值下 `ECO_SOLID = #122822`（深炭绿）
  - → 结论：**深色套值完全没被应用**，不是 MinePage 的适配缺口
- 逐层核查结论：MinePage 代码**完全正确**（有 `@StorageProp('themeTick')`、根底取 `EcoTheme.bgSolid(ecoLevel)`、内层 Column 恒读 themeTick）；EntryAbility 也调了 `ThemeMode.init()`；`prefs()` 的 STORE 名与 LocalStore 同库不同键，不冲突。
- **真根因**：`ThemeMode.init()` 把「读盘失败」与「读盘成功但 dark=false」混为一谈，且 catch **完全静默**。一旦 `prefs()` 抛错（最可能：`AppStorage('appContext')` 尚未注入—— onCreate 里 setOrCreate 与本调用同帧，跨语言初始化顺序不可靠），**整段 try 块被跳过** → `applyDark` 永不执行 → 表现「设置里开了深色，重启后全应用仍是浅色」，且无任何报错可查。
- **修复**：init 拆成三步独立兜底，每步失败单独处理 + `console.warn` 留日志：
  ① 取 preferences（失败 → 只放弃持久化，仍走完换血流程）
  ② 读 dark（失败 → 沿用内存态）
  ③ 读 quality（失败 → 沿用当前档位；**绝不能连坐②**，画质与明暗是两个独立开关）
  `bumpRender()` 移到 try 之外，**无论读盘成功与否都要推**（失败时也可能是「内存态已深色但页面用早期浅色值建过」）。
- 方法论沉淀：**用户报「某页没适配」时，先取像素比对浅/深两套令牌值**。值精确等于浅色套值 = 换血没生效（全局问题）；值是「浅色样式但该用深色」= 页面级适配缺口。这个判定能省掉大量无效的页面级排查。

## 液态玻璃「阴影/暗角很脏」终局根因：渐变停靠点把底色挖空了（结构性）

  都是「哪个暗层 alpha 大」（外投影 → 描边暗缝 → Shadow.card），治标不治本。
- **本轮做法**：先逐像素复算，而不是继续猜暗层。写 `grad_sim.py` 把
  `surface()` 的停靠点、ArkUI 逐通道 RGBA 插值、页面底色实测值 (241,250,247)
  完整复现 → 得到 t=0.92~0.96 处「比页面底暗 28~39 级」的灰色带，
  与截图实测暗角 (199,208,205) **逐值吻合**；同一条复算也解释了
  「卡片内部 (239,248,245) ≈ 页面底」这一长期被忽略的现象。
- **真根因（`GlassLight.surface()`，两个叠加的结构错误）**：
  1. washColors 的停靠点被**原样**塞进 `.linearGradient()`，而 wash 在
     0.55~0.90 之间 alpha=0、底色只出现在 t=0/1 两个端点 →
     **卡片中段全透明**，根本没有白色玻璃底（卡片看起来「不存在」，
     只剩 1px 描边和那块脏雾）。
  2. 0.90 的深墨停靠点直连 1.00 的白底停靠点 → ArkUI 不预乘插值，
     中段插出 rgba(≈132,135,134,0.37) 的半透明灰 → 右下角一块
     硬边斜切灰斑（0.90 处从「全透明」突变成 1.8% 深墨，所以边界极硬）。
  3. 同一个坑还解释了历史悬案「选中 chip 白底白字」（品牌实底也只有两端点）。
- **修复**：新增 `GlassLight.rgbaOf()` / `GlassLight.over()`，`surface()` 改为
  **先把每个光照停靠点 α 合成到底色上再进渐变**。停靠点自带完整底色 →
  中段不再透明、任意两点插值只在「同一块玻璃的亮/暗部」之间过渡。
  实算新结果：卡片通体比页面底 **+10 级**，到右下角单调收到 +5.6 级，
  **全程无一处比底色暗**（浅色 7 种玻璃底色 + 深色 7 种全部 PASS）。
- 顺手根治两处同族问题：
  - `Index.OrbButton` 的「＋」圆钮把「白 0.78 → 深墨 0.10 → 深墨 0.22」
    直接相邻写进渐变（右下角一块脏暗斑，深墨 22% 太狠）→ 抽成
    `GlassLight.orbSurface()` 预合成，终端深墨收到 0.09。
  - 浅色外投影再收一档：`shadowOf` 三档 → alpha 0.8%~1.2% / radius 8~12；
    `Theme.Shadow.cardColor` → `#03000003`（alpha 1.2%）。
    理由：卡片本体已比页面底亮 10 级，任何 >1.5% 的黑投影都会压出一圈灰晕。
- **教训（写进排查口诀）**：
  1. 「玻璃里有暗斑」先查**渐变停靠点是否把底色挖空**，再查暗层 alpha。
     `rgba` 停靠点里出现 `alpha=0` 或「深→白」直连 = 必然插出灰带。
  2. ArkUI `linearGradient` 不预乘插值 → 混色（高光/阴影）必须**先 over
     到底色**再用，不能当作独立停靠点。这条对卡片、胶囊、圆钮、chip 通用。
  3. 单层合成渐变的停靠点位置直接用归一化位置（0/0.12/0.38/0.55/0.90/1），
     不需要再收进 [0.02,0.90] 去躲「重复停靠点」——那是上一个 bug 的补丁。
- 构建：BUILD SUCCESSFUL（CompileArkTS 0 error / 改动文件 0 warning），
  已确认 `modules.abc` 内含新符号 `orbSurface` / `rgbaOf`。

## 自动刷新仍然失效 → 上一轮的诊断是错的：`onStorageChange` 根本不是生命周期
- 用户再次反馈「记录要手动刷新 / AI 识别成功后数据不自动刷新」。上一轮（见上条）
  以为是「只有前台 Tab 才触发」，于是加了 activeTab 分支 —— 但**前提本身就是错的**。
- **真正根因**：32 个页面写的是 `@StorageLink('ecoTick') ecoTick` + `onStorageChange(key)`，
  而 **ArkUI/SDK 里不存在 `onStorageChange` 这个回调**（SDK d.ts 全量 grep：NOT FOUND）。
  `@StorageLink` 只会把组件标脏重建，**重建时读的还是旧数据**；
  于是无论前台后台、无论 ecoTick 涨到多少，`load()` 从未被执行过 ——
  这才是「必须手动刷新」的唯一原因，与 Tab 前后台无关（上一轮的 activeTab 补丁也是死信）。
- 数据层一直是好的：`DataSource.addRecord/removeRecord` 内部已
  `broadcastDataChange()` → `bump()` → `ecoTick +1`（备份恢复/清空/演示还原也都广播了）。
- **修复（32 文件，行级批量）**：
  ① `@StorageLink('ecoTick') @Watch('onEcoTick') ecoTick: number = 0`
  ② 桥接方法 `onEcoTick(): void { this.onStorageChange('ecoTick') }`（复用各页原有逻辑，零重写）
  ③ 记录页再补 `@StorageLink('activeTab') @Watch('onActiveTab')`（切回本 Tab 兜底重拉）
  校验：`@Watch('onEcoTick')` 32 个 / `onEcoTick()` 定义 32 个，逐文件一一配对。
- **顺带修刷新可靠性**：DashboardPage.load 的 `if (inFlight) return` 会吞掉飞行期间
  到达的「数据真的变了」触发（连记两笔时第二次丢）→ 改 `loadPending` 折叠，
  本次结束后补拉一次；既不丢触发也不会并发覆盖。
- 文档：方案文档新增「## 7. 数据自动刷新链路」（链路图 + onStorageChange 教训 +
  可靠性表），验收清单/排查口诀同步更新。
- 构建：BUILD SUCCESSFUL（CompileArkTS 0 error；pages/ui 0 warning）。
- 方法论：**「某个回调没被调用」的第一反应应该是 grep SDK d.ts 确认它存在**，
  而不是猜调用时机。注释里写「XX 会调用这里」不等于框架真的会调。

## ⚠️ 编码踩坑（第二次，务必记住）：绝不能用 pwsh 改写含中文的文件

## 深色模式「没适配」根因：不跟随系统 + metadata 强制歧义（最新一轮）

     - `setDark()`：置 manualOverride=true + 持久化 lock，经 `applyTheme()` 换血+广播。
     - `onSystemColorModeChange(isDark)`：仅未手动锁定时跟随系统实时切换。
  ③ EntryAbility：`onCreate` 用 `this.context.config.colorMode`(`ConfigurationConstant.ColorMode.COLOR_MODE_DARK`)

  ④ 碳情绪 Hero 渐变（EcoMood.*_FROM/TO）在 applyDarkValues 中**本就保留浅色值不变**，
     已满足「保留碳情绪原有颜色」。

## 深色液态玻璃质感修复（截图取证驱动，非猜测）

**用户诉求**：「全局深色要这种效果，修复一下深色模式液态玻璃」+ 深色记录页截图。

**取证方法**（首次落地，很有效）：Pillow 逐像素扫描截图 817×920，
分区取**中位亮度**（避开文字/emoji 干扰），反解 alpha 定位病灶。

**关键实测数据**：
| 区域 | 内部L | 1px边L | 倍数 |
|---|---|---|---|
| 卡片 | 49 | **156** | 3.2× |
| 底部胶囊 | 48 | **104** | 2.2× |
| 筛选chip | — | **190** | 惨白 |
| 圆钮 | — | **160** | 死白球 |

**根因一：1px 受光描边过亮**（主病灶）
- 反解 `L = 49 + 194·a = 156 → a ≈ 0.55`，正好是 `edgeBorderAlphaDark` 的 0.55×darkAdapt。
- 为什么以前没暴露：菲涅尔渐变层（fresnelColors，9% 带宽渐隐亮带）原本与
  1px 描边共存构成自然边缘，但 **GlassLightLayers 已在 Index.ets 弃用**
  → 描边成为唯一边缘线索，过亮被完全暴露。
- 修：edgeBorderAlphaDark 0.55/0.62/0.50 → **0.18/0.22/0.16**（上限 0.26）；
  同时 darkAdapt 1.18/1.08 → **1.10/1.05**（它是乘性放大器，会把降下来的值又顶回去）。
- 预测复核：卡片边 L 从 156 → **97**（1.55×），玻璃面 +15 级层级不变。

**根因二：深色套值饱和度过高（森林绿）**
- 卡片实测 #1C3934 **饱和度 0.51**、页面底 0.55 —— 是饱和绿，不是深色玻璃。
- 根因：`*_SOLID` 照抄浅色「淡薄荷」色相，但 alpha 提到 1.0 填满整屏后，
  浅色里几乎无感的绿相被放大成整屏绿。玻璃的材质感应来自「中性暗面 + 极轻冷调」，
  绿相该由品牌与碳情绪提供，**不该由中性底色提供**。
- 修：Neutral.BG/CARD/SURFACE 去饱和；EcoMood 四个 *_SOLID 压到 0.30~0.38；
  Brand.SPLASH 渐变同改。页面底饱和度 0.55 → **0.33**。
- 对比度复核仍达标：正文 10.78:1、副文 5.53:1（AA 需 4.5）。

**配套改动**：
- `washColors` 深色停靠点重排（原 0.52 有全透明断点 → 被 surface() over 到底色后
  形成斜向亮带）：改为 0/0.16/0.34/0.50/0.62/0.88/1 单调下沉，无断点。
- `washAlphaDark` 0.05 → **0.07**：菲涅尔层没了，描边又降 60%，
  受光感几乎全靠这条 135° 渐变承担，不补会塌成「灰片 + 淡边」。
- `orbSurface` 深色 lit 0.10/0.20/0.28 → **0.05/0.09/0.13**，底染 0.10→0.09
  （圆钮原来中位 L=160，是环境 34 的 4.7 倍，截图里是死白球）。
- `RecordListPage` 筛选药丸白边 0.55/0.38 硬编码 → 深色下 0.22/0.14
  （药丸底色 EcoTheme.primary 保持碳情绪薄荷原色不动）。
- `Index.ets` 底部胶囊/圆钮描边：深色硬编码 0.26 / 0.42|0.28 → 全走
  `GlassLight.borderColors`，不再绕过光照模型。
- 构建：BUILD SUCCESSFUL（34s，0 error）。

**方法论沉淀**：
1. 「玻璃太亮/太脏」先用**分区中位亮度**定位是玻璃面还是描边的问题——
   两者差 3 倍就是描边过亮，不是玻璃底色错。
2. 反解 `L = 底 + (边−底)·a` 可从截图直接算出 alpha 超出真实代码值多少。
3. **改乘性系数（darkAdapt）前必须先改被它放大的基数**，否则白改 ——
   本轮就是先砍 edgeBorderAlphaDark，又发现 darkAdapt 1.18 把它顶回 0.21。
4. 文本/emoji 会污染亮度统计，**必须取中位数而非均值/单点**。

## CfStatTile 三宫格溢出修复（用户圈出「右侧多条边」）

**用户诉求**：「红圈有个多余UI」（记录页截图，红圈圈住「减排放累计」卡右侧

## BehaviorDetailPage「记录不存在」修复（入口没传参的死路）

**用户诉求**：「记录详情没有修一下」（附空态页截图：🔍 记录不存在 / 它可能已被删除）。

**根因（传参链路断裂）**：
本项目因 PageMap 已提供 NavDestination 容器（页面内部拿不到
NavDestinationContext.onReady），**统一约定：参数走 AppStorage 传参**，
即 `goWithParam(route, key, value)` 先 `AppStorage.set` 再 push，
目标页在 `aboutToAppear` 读取并 delete。

全库 grep 发现**设置页**「低碳记录」入口直接调
`AppRouter.pathStack.pushPathByName(RouteName.BEHAVIOR_DETAIL, null)` ——
**没走 goWithParam、没写 detailRecordId** → 详情页 `AppStorage.get` 得到
undefined → recordId 保持 -1 → load() 直接 return → 永远空态。
列表页(RecordListPage:323)走的是 goWithParam，所以只有设置页这条是死路。

**修复（三层）**：
① **入口修好**：SettingsPage 新增 `@State latestRecordId`，
   `load()` 里顺带 `DataSource.records()` 取 `list[0].recordId`
   （已核实 `LocalStore.allRecords()` 按 behaviorTime **倒序**，取 [0] 即最新）；
   `onItemTap` 对 BEHAVIOR_DETAIL 走新的 `openLatestRecord()` →
   `goWithParam(BEHAVIOR_DETAIL, 'detailRecordId', latestRecordId)`；
   无任何记录时不跳空页面，toast「还没有低碳记录，先去记录一笔吧」。
② **页面兜底**：`load()` 去掉 `if (recordId < 0) return` 的硬失败，
   改为「id 缺失/记录已删 → 回退展示最新一条」，将来再有入口漏传也不会白屏。
③ **空态文案纠偏**：只有库真为空才显示空态，文案从
   「记录不存在 / 它可能已被删除」改为「还没有低碳记录 / 回到记录页，点击 ＋…」，
   避免用户误以为数据丢了。

**顺手修的同源半成品**：`doDelete()` 原是
`setTimeout(600ms) + toast('记录已删除')` —— **记录根本没被删**，
注释写着「本地移除后回退详情」但移除那步从没写。
改为真调 `DataSource.removeRecord(id)`（其内部会 broadcastDataChange，
列表/统计/碳档位同步刷新），按返回 bool 区分「删除成功」与「记录已不存在」，
成功后置 `gone = true` 再 pop 防连退两级。`doDelete` 改为 async。

**全库审计结论（同类死路排查）**：
需要参数的详情页只有 3 个 —— BehaviorDetail / ArticleDetail / CertificateDetail，
三者全部入口均已用 goWithParam 正确传参；其余 23 处 pushPathByName
指向的都是无需参数的页面。**没有第二个同类 bug**。

**构建**：BUILD SUCCESSFUL（23s，0 error）。

**方法论沉淀**：
1. 「push 进去却显示不存在/空态」= **传参链路断裂**，先 grep 目标页读的是哪个
   AppStorage key，再回查所有 push 该路由的入口是否都走了同一个传参出口。
   本项目唯一传参出口是 `goWithParam`，绕过它 = 必坏。

## 科普页分类 chip 被裁（Flex 折行的隐性压窄）

**用户诉求**：「再改这里不方便看」（截图：白色「全部」chip 被裁掉一半，
「减排技巧」孤行掉到第二行）。

**取证**（截图逐像素扫白色块边界）：
```
白色 chip: x=245..497   左边缘 245 < 内容边界 250 → 被裁 5px
第二行: 仅 x=248..340 一个 chip（减排技巧）→ 孤行
```

**根因：`Flex({wrap: FlexWrap.Wrap})` 的折行不是"整体换行"，而是"先压窄第一行"**。
4 个 chip 都是 fit-content，总宽超出容器时 Flex 会**压缩第一行的项**去填满，
而不是把溢出的项整体挪到下一行 → 第一行 chip 被压窄（白色 chip 圆角+文字一起被切），
第 4 个才换行成孤行。注释里写的「每个 chip 都完整可见」在窄屏下并不成立。

**修复：改为实测宽度 + 均分格宽（全库统一范式）**
① `ArticleListPage`：外层包 `Column` + `onAreaChange` 测宽 →
   `chipCellW() = (容器宽 - 间隔) / CHIP_PER_ROW`；每个 chip 外层 `Column`
   定宽 `chipCellW()`，文字加 `maxLines(1) + Ellipsis` 兜底。
② **`CHIP_PER_ROW = 2`（2×2）**：4 个分类排 3 列时第 4 个必然孤行，2×2 是
   唯一不留孤行且够宽放下四字标题的排法。
③ `GlassPill` 新增 `fillWidth: boolean = false` 开关：
   默认保持 fit-content（chip/收藏钮排在横向 Row 里，百分比宽会撑满整行），
   仅在均分排版场景由调用方开启。实现用
   `.width(this.fillWidth ? '100%' : 'auto')` ——
   **`undefined` 过不了 ArkTS 静态检查，用 `'auto'` 等价**。

**编译踩坑**：@BuilderParam 的 slot 内容闭合后**不能再挂修饰符链**
（`.width('100%')` 写在 slot 的 `}` 之后 → `Declaration or statement expected` +
`Cannot find name 'width'`）。药丸宽度必须通过组件参数（fillWidth）传递。

**构建**：BUILD SUCCESSFUL（26s，0 error）。

**方法论沉淀**：
1. **`FlexWrap.Wrap` 会压窄首行项**，不是整体换行。要「每项等宽且完整」，
   必须**给每项显式定宽**（父级均分），不能依赖 fit-content 让 Flex 自己排。
2. `chip 排版不整齐` 有三种根因，要分清：① fit-content 压窄（本例）
   ② 文字未锁 `maxLines(1)` ③ 缺 ellipsis。均分 + 锁行 + 省略号 = 三件套。
3. ArkUI 里「不设宽度」不能写 `undefined`，用 `'auto'`（width）或
   `0`（layoutWeight）表达。
4. @BuilderParam slot 的闭合 `}` 之后不能再链式调用属性。

### 20:14 植树棵数与证书夹口径统一（用户截图反馈「2 棵树却无证书」）

- **根因**：`LocalStore.stats()` 里 `treeCount = floor(累计获得积分/200)` 是**等价折算**（553 分 ≈ 2 棵），而证书夹走 `exchangedPoints`（真实兑换 = 0），两套口径同屏打架。
- **修法**：`treeCount` 统一改为**真实兑换口径**（与植树证书同源，每 200 分兑换 1 棵 = 1 张证书）——`LocalStore.stats()` 与 `MockStore` 两处统计同步；兑换通道未上线前恒为 0，与「证书夹 0 张」「累计兑换 0」完全一致。

- **验证**：BUILD SUCCESSFUL（28.6s），签名包 20:14:43 晚于全部 7 处源改动。
- **方法论**：`treeCount` 这类"既有折算含义又有交易含义"的字段，多页同屏展示时必须锁定单一口径（真实交易），等价换算另起独立计算（treesOf），绝不共用一个字段。
