## 修复 DevEco 构建报错 "The target can not be empty ... applyToProducts"

**现象**：DevEco Studio 打开 `D:/11/HongmengiHuanbao/app` 后构建失败，报
"The target can not be empty. Check the build-profile.json5 file of the project root
directory and make sure the targets of the modules in configuration is set to
specified product: default in applyToProducts."

**根因**：`app/build-profile.json5` 的 `app.products[0]` 里
`compileSdkVersion` / `targetSdkVersion` 被写成字符串 `'26.0.0'`。
项目 `runtimeOS` 是 `OpenHarmony`，hvigor 6.1.1 规则是 API>=10 时这两个字段**必须是数字**。
非法值导致 product "default" 校验失败被丢弃 → 模块 target "default" 绑不到任何 product
→ 报 "target can not be empty" 并给出 applyToProducts 的误导性提示。
（`modules[].targets[].applyToProducts: ["default"]` 本身是对的，不用改。）

**修复**：`compileSdkVersion` / `targetSdkVersion` 改为数字 `24`
（= 本机 OpenHarmony SDK 的 apiVersion）。

**本机环境事实（重要）**
- DevEco Studio 6.1.1.418 → `C:\Program Files\Huawei\DevEco Studio`（旧的 `D:\anzhi\DevEco Studio` 不存在）
- OpenHarmony SDK → `D:\openhongm`（版本化布局：`12/ 23/ 24/ 26.0.0/`，其中只有 `24` 有完整组件）
  - 路径规则：`<sdk.dir>/<api>/{ets,js,native,previewer,toolchains}`
  - DevEco 自带的 `sdk/default/openharmony` 是 HarmonyOS 布局，**不兼容** OpenHarmony 模式，别用
- IDE 配置 `oh.sdk.location = D:\openhongm` 本身是对的

**附带修复**
- 新建 `app/local.properties`（已被 .gitignore 忽略）：`sdk.dir=D:/openhongm`，CLI 构建必需
- 重写 `app/build-check.ps1`：自动探测 DevEco 路径（原写死 `D:\anzhi\...` 已失效）、
  自动补 local.properties、修正 Where-Object 单结果退化成字符串导致 `[0]` 取到首字符 "C" 的 bug、
  补 UTF-8 BOM（PS 5.1 无 BOM 会按 GBK 读导致中文注释语法错误）
- 运行方式：`powershell -ExecutionPolicy Bypass -File build-check.ps1`

**验证**：`BUILD SUCCESSFUL`，产出 `app/entry/build/default/outputs/default/entry-default-signed.hap`（18.7 MB）

**参照工程**：`D:/11/carbon-master/app` 是同源的老工程且能正常构建，其 build-profile.json5
用数字 24，可作对照基准。

## 修复：兑换第 2 棵树时第 1 棵的树种名被覆盖

**现象**：积分商城（碳权益兑换页）3000 分兑换「公益植树认养」后，证书夹里树的
树种名在第二次兑换时被顶掉（梭梭树 → 沙枣树 → 胡杨…），且证书列表恒定只有一张。

**根因**：`MockStore.certificatesFrom(exchangedPoints)` 把**所有兑换积分聚合成一张**
汇总证书（certId 写死 700），树种名靠 `names[totalTrees % 4]` 推导 ——
累计棵数一变，全表唯一那张证书的树种名就跟着变；第 2 棵树根本没有自己的证书。
代码原注释已预告该问题（「届时改为按每笔兑换流水各生成一张」）。

**修复**：改成**以券为流水单元** —— 每张 `kind='tree'` 的兑换券 = 1 棵树 = 1 张独立证书。
- `MockStore.certificatesFrom(treeCoupons: LocalCoupon[])`：逐券开证
  - `certId` = 签发时间戳 × 100 + 券号散列尾数（详情页按 id 定位，须稳定唯一）
  - `certNo` = 'CF-' + yyyyMMdd + HHmm + 4 位散列（列表页 ForEach 的 keyGenerator，须唯一）
  - `treeType` = `names[hash(couponId) % 4]` —— **绑定在券号上**，与已兑换总棵数无关
  - `treeCount` = 1、`costPoints` = 3000、`issueDate` 取券的 issuedAt
- `LocalStore.treeCoupons()`：返回 kind='tree' 的券，按 issuedAt 倒序
- `DataSource.certificates()`：改为 `MockStore.certificatesFrom(LocalStore.treeCoupons())`
- 新增 `hash32`（djb2）/ `pad4` 辅助函数

**哈希选型**：用 djb2 而非 FNV-1a —— FNV 乘子 16777619 会让中间值超出 2^53 丢精度；
精确 32 位乘法要靠 `Math.imul`，ArkTS 标准库不保证提供。djb2 乘子 33，`h*33 < 2^53` 全程精确。

**验证**：Node 复现「兑 1 棵 → 兑 2 棵」，第 1 张证书的编号/树种/id 三者完全未变；
certId/certNo 均唯一；clean 构建 BUILD SUCCESSFUL（29s）。

## 修复：Preview 构建报 00303221 权限配置错误 + PreviewArkTS 编译错误

**现象**：`PreviewBuild` 在 PreBuild 阶段报错 `ohos.permission.READ_MEDIA_IMAGES ... must be a
value that is predefined within the SDK`，且（权限修好后）PreviewArkTS 又报
`PhotoAccessHelper.getInstance` 不存在 + `arkts-no-any-unknown`。

**根因**：
1. `READ_MEDIA_IMAGES` 是 **HarmonyOS NEXT（华为闭源分支）** 的细分权限，本机 OpenHarmony
   API 24 SDK 不认（SDK 只有 `READ_MEDIA` / `WRITE_MEDIA` / `MEDIA_LOCATION` 等）。项目
   runtimeOS=OpenHarmony，必须用 OpenHarmony 的权限命名。
2. `AiVisionRecognizer.openFd()` 里用了两个本 SDK 不存在的 API：
   - `photoAccessHelper.PhotoAccessHelper.getInstance(ctx)` → 正确是 `getPhotoAccessHelper(ctx)`
   - `helper.getAssetsByUris([uri])` → 本 SDK 无此方法
   且这段其实永远走 catch 兜底到 `fs.openSync`（死代码），只是之前被权限错误挡住没暴露。

**修复**：
- `entry/src/main/module.json5`：`READ_MEDIA_IMAGES` → `READ_MEDIA`（OpenHarmony 读媒体权限）
- `entry/src/main/ets/data/ai/AiVisionRecognizer.ets`：删除那段死代码，`openFd` 对
  content:// URI 直接 `fs.openSync(uri, READ_ONLY)` —— 这正是 OpenHarmony 对
  PhotoViewPicker 返回 URI 的标准读法（选择器已授予临时读取权限，无需 READ_MEDIA）。

**验证**：`PreviewBuild`（去掉 --watch）BUILD SUCCESSFUL（16s）。

**备注**：改完后全工程已不再有任何"直接遍历媒体库"的代码（只有 PhotoViewPicker + fs.openSync），
`READ_MEDIA` 现在是"声明但未实际使用"。保留无害、且日后加媒体库浏览即可用；如想干净也可删。
